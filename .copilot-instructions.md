# Copilot Instructions for Cities Game Web Application

## Standard Web Application Engineering Best Practices

### Code Quality Standards

#### TypeScript/JavaScript

- **Always use explicit types** - Never use `any` without strong justification
- **Prefer interfaces over types** for object shapes that might be extended
- **Use strict TypeScript configuration** - Enable all strict checks in tsconfig.json
- **Handle errors explicitly** - Use proper error types instead of `any` in catch blocks
- **Validate inputs** - Always validate data at API boundaries and user inputs
- **Use meaningful variable names** - Avoid abbreviations and single-letter variables
- **Keep functions small** - Functions should do one thing well (max 20-30 lines)
- **Prefer composition over inheritance** - Use functional patterns where appropriate

#### React/Frontend

- **Use functional components** with hooks instead of class components
- **Keep components focused** - Single responsibility principle
- **Extract custom hooks** for reusable stateful logic
- **Implement proper error boundaries** for graceful failure handling
- **Use proper dependency arrays** in useEffect to prevent infinite loops
- **Memoize expensive calculations** with useMemo and useCallback when needed
- **Prefer controlled components** over uncontrolled for form inputs

#### Node.js/Backend

- **Use environment variables** for configuration - Never hardcode secrets
- **Implement proper logging** with structured logs (JSON format preferred)
- **Handle async operations properly** - Always handle Promise rejections
- **Use middleware for cross-cutting concerns** (authentication, logging, CORS)
- **Implement proper input validation** using libraries like Zod or Joi
- **Use connection pooling** for database connections
- **Implement graceful shutdown** handling for cleanup operations

### Security Best Practices

- **Validate all inputs** at API boundaries
- **Use parameterized queries** to prevent SQL injection
- **Implement proper authentication** and authorization
- **Use HTTPS in production** and secure headers
- **Keep dependencies updated** and audit for vulnerabilities
- **Implement rate limiting** for API endpoints
- **Sanitize user outputs** to prevent XSS attacks
- **Use proper CORS configuration** - Don't use wildcard origins in production

### Testing Standards

- **Write tests for critical business logic** - Aim for >80% coverage on core functions
- **Use descriptive test names** that explain the expected behavior
- **Follow AAA pattern** - Arrange, Act, Assert
- **Mock external dependencies** properly to isolate units under test
- **Test error conditions** not just happy paths
- **Use integration tests** for API endpoints and critical user journeys
- **Run tests in CI/CD pipeline** and block deployments on test failures

### Performance Guidelines

- **Optimize database queries** - Use indexes, avoid N+1 queries
- **Implement caching strategies** for frequently accessed data
- **Use lazy loading** for large datasets and images
- **Minimize bundle sizes** - Tree shake unused code, code splitting
- **Optimize images** and use appropriate formats (WebP, AVIF)
- **Implement proper pagination** for large data sets
- **Use CDN** for static assets in production

### Git and Version Control

- **Use conventional commits** - Follow format: `type(scope): description`
- **Keep commits atomic** - One logical change per commit
- **Write meaningful commit messages** that explain why, not what
- **Use feature branches** and pull requests for all changes
- **Review all code** before merging - No direct pushes to main
- **Keep history clean** - Squash or rebase feature branches before merge
- **Tag releases** with semantic versioning

### Documentation Standards

- **Document all public APIs** with comprehensive examples
- **Keep README.md updated** with setup and running instructions
- **Document environment variables** and configuration options
- **Include troubleshooting guides** for common issues
- **Maintain CHANGELOG.md** for release notes
- **Use JSDoc comments** for complex functions and classes

### Deployment and Infrastructure

- **Use Infrastructure as Code** - Define infrastructure in version control
- **Implement health checks** for all services
- **Use blue-green or rolling deployments** to minimize downtime
- **Monitor application metrics** and set up alerting
- **Implement proper backup strategies** for data
- **Use secrets management** for sensitive configuration
- **Implement proper logging and monitoring** in production

## GitHub Actions Debugging Workflow

### 🚨 TERMINAL SAFETY FIRST 🚨

**NEVER use commands that will hang in interactive mode:**

- ❌ `less`, `more`, `vi`, `nano`, `emacs`
- ❌ `gh run view [ID]` without `| cat`
- ❌ Any command that opens a pager or editor

**ALWAYS use safe alternatives:**

- ✅ `cat file.txt | head -50`
- ✅ `gh run view [ID] | cat`
- ✅ `grep "pattern" file.txt | head -20`
- ✅ Commands that return to prompt immediately

### Mandatory Debugging Process

When any GitHub Actions workflow fails, **ALWAYS** follow this exact process:

#### Step 1: Monitor Latest Changes

```bash
# Check status quickly (safe, returns to prompt)
gh pr checks

# ONLY use --watch when actively monitoring completion
# WARNING: This will keep running until workflow completes
gh pr checks --watch
```

- **Wait for the complete workflow to finish** - Don't start debugging partial results
- Note which specific jobs are failing vs. succeeding
- Identify if failures are consistent or intermittent
- **Use Ctrl+C to exit watch mode when workflow completes**

#### Step 2: Download Complete Logs

```bash
# Get the latest run ID (safe, single line output)
gh run list --limit 1 --json databaseId --jq '.[0].databaseId'

# Download logs for the failed run (safe, downloads to directory)
gh run download [RUN_ID] --dir ./github-logs

# Or download logs for specific job (safe, creates zip file)
gh api repos/:owner/:repo/actions/runs/[RUN_ID]/logs --output run-logs.zip

# SAFELY examine log files (NEVER use less/more/vi)
find ./github-logs -name "*.txt" | head -10
cat ./github-logs/*/[JOB_NAME]/[STEP_NAME].txt | head -100
grep -i "error\|fail" ./github-logs/*/*.txt | head -20
```

**CRITICAL: Always use `| head`, `| tail`, or `| cat` to prevent hanging in pagers**

#### Step 3: Analyze Error Messages

- **Extract ALL error and warning messages** from the log files
- **Focus on the first failure** - Later failures may be cascading effects
- **Look for specific error codes** and module resolution issues
- **Check for environment differences** (Node version, dependencies, paths)
- **Identify patterns** across multiple failed jobs

#### Step 4: Local Validation Before Fixes

**NEVER push fixes without local validation:**

```bash
# Test the exact commands that failed in CI
cd backend && npm install
cd backend && npm run lint
cd backend && npm run type-check
cd backend && npm run test

cd frontend && npm install
cd frontend && npm run lint
cd frontend && npm run type-check
cd frontend && npm run test
```

#### Step 5: Root Cause Analysis

Common GitHub Actions failure categories:

- **Environment issues**: Node version, dependency installation
- **Path/directory issues**: Working directory, relative paths
- **Permission issues**: GitHub token, security-events access
- **Caching issues**: Stale or corrupted cache data
- **Dependency issues**: Version conflicts, missing packages
- **Configuration issues**: Missing files, incorrect settings

#### Step 6: Targeted Fixes

- **Fix ONE issue at a time** - Don't batch multiple unrelated fixes
- **Test locally first** - Ensure the fix works in your environment
- **Use descriptive commit messages** explaining the specific fix
- **Document the root cause** in commit messages for future reference

#### Step 7: Iterative Testing

```bash
# After implementing fix
git add .
git commit -m "fix: specific description of what was fixed"
git push origin branch-name

# Monitor the new run
gh pr checks --watch
```

### GitHub Actions Best Practices

#### Workflow Configuration

- **Use specific action versions** (@v4, not @latest) for reproducibility
- **Set explicit permissions** for security jobs
- **Use working-directory** instead of cd commands
- **Cache dependencies properly** with correct dependency paths
- **Use matrix strategies** for testing multiple versions
- **Implement proper secret management** for sensitive data

#### Job Dependencies and Parallelization

- **Run linting and security scans in parallel** to save time
- **Make integration tests depend on** lint and unit test success
- **Use job outputs** to pass data between jobs when needed
- **Implement proper cleanup** for test artifacts and temporary data

#### Error Handling and Debugging

- **Add debug output** to understand job execution context
- **Use continue-on-error: true** selectively for non-critical steps
- **Implement proper timeout values** to avoid hanging jobs
- **Upload artifacts** for debugging failed test runs

### Debugging Commands Reference

**CRITICAL: Terminal Safety Rules**

- **NEVER use commands that open interactive editors** (like `less`, `more`, `vi`, `nano`)
- **ALWAYS pipe output to `head`, `tail`, or `cat`** for large files
- **Use `--watch` flag sparingly** and only when explicitly monitoring for completion
- **Add timeouts or limits** to prevent infinite loops

```bash
# Check current PR status (safe, returns to prompt)
gh pr checks

# Watch for completion (ONLY when actively monitoring)
gh pr checks --watch

# List recent workflow runs (safe, limited output)
gh run list --limit 5

# Get specific run details (safe, formatted output)
gh run view [RUN_ID]

# Download run logs (safe, downloads files)
gh run download [RUN_ID]

# View log files safely (prevent hanging in pager)
cat ./github-logs/*/[JOB_NAME]/[STEP_NAME].txt | head -100

# Search for errors in logs (safe, limited output)
grep -i "error\|fail\|warning" ./github-logs/*/*.txt | head -20

# View specific lines from log files
head -50 log-file.txt
tail -50 log-file.txt

# Cancel a running workflow
gh run cancel [RUN_ID]

# Re-run a failed workflow
gh run rerun [RUN_ID]

# View workflow file safely (prevent pager)
gh workflow view [WORKFLOW_NAME] | cat

# Safe file examination (NEVER use less/more/vi)
cat file.txt | head -50
cat file.txt | tail -50
grep "pattern" file.txt | head -20
```

### File Viewing Safety Guidelines

**ALWAYS avoid these commands in terminal:**

```bash
# ❌ NEVER USE - Will hang in editor/pager
less file.txt
more file.txt
vi file.txt
nano file.txt
emacs file.txt
gh run view [ID]  # without | cat

# ✅ SAFE ALTERNATIVES - Return to prompt
cat file.txt | head -50
cat file.txt | tail -50
head -n 50 file.txt
tail -n 50 file.txt
grep "pattern" file.txt
gh run view [ID] | cat
```

## Emergency Debugging Checklist

When CI is completely broken:

1. ✅ **Verify local environment works** - All tests pass locally
2. ✅ **Check Node.js version consistency** - Local vs CI
3. ✅ **Verify dependency installation** - npm install vs npm ci
4. ✅ **Check file paths and working directories** - Relative vs absolute
5. ✅ **Validate GitHub Actions syntax** - YAML formatting, proper indentation
6. ✅ **Check permissions and secrets** - Proper access for security scans
7. ✅ **Review recent changes** - What changed between working and broken state
8. ✅ **Test individual commands** - Run CI commands locally
9. ✅ **Check for environment-specific issues** - Case sensitivity, path separators
10. ✅ **Validate cache and dependency management** - Clear cache if needed
